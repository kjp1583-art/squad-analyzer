# 🔁 자동 개선 루프 — 헌장

사장님 지시(2026-09-27): "이 프로젝트를 너가 주도적으로 생각해서 개선 루프를 만들고, 스스로 계속 업그레이드".
매일 한 번 루틴이 새로 깨어나 이 파일을 읽고 그대로 따른다. **기억은 이 폴더의 파일뿐**이다 — 대화는 회차마다 새로 시작한다.

- `LOOP.md` — 이 헌장(규칙·절차). 루프가 스스로 고치지 않는다(사장님·세션 주인만).
- `backlog.md` — 할 일 목록. 루프가 추가·갱신한다. 사장님이 `[승인]` 을 붙이면 B등급도 진행.
- `log.md` — 회차 기록(맨 위가 최신). 다음 회차가 "지난번에 뭘 했나"를 여기서 본다.
- `signals.py` — 신호 수집 스크립트.

저장소: `kjp1583-art/squad-analyzer`(분석기·웹·툴링) · `kjp1583-art/squad-naejeon-bot`(봇).
두 저장소의 `CLAUDE.md` 규칙이 이 헌장보다 우선한다(패치노트·장비 끼운 테스트·십이귀월 3곳 동기·주간스쿼드·배포·금지 사항).

## 목표
클랜원이 문제를 먼저 발견하기 전에 루프가 찾아 고친다. 우선순위:
1. **운영 오류** — 봇 예외, 배포가 안 올라감, 분석기 기록 누락·결과 대기 고착
2. **데이터 무결성** — 시트 오염(KDA 날짜 변환·중복행·10명 아닌 판), 타이틀·포인트 원장 불일치
3. **신뢰성·성능** — 메모리(봇 한도 ≈256MB, 2026-09-05 OOM), 429, 재시도, 조용한 실패(로그 없는 보류)
4. **다듬기** — 이미 있는 기능의 헷갈리는 안내문·죽은 버튼·빠진 로그

## 자율 등급 — 무엇을 혼자 배포해도 되나
**A등급(혼자 배포)**: 증거가 있는 버그·예외 수정, 데이터 무결성 수정(앞으로 쓰는 코드), 로그·관측 추가, 성능·메모리 개선.
조건: 재현 또는 근거(오류 위치·시트 행·로그) + 테스트 통과 + 독립 검토(아래 5단계).

**B등급(제안만 — 사장님 `[승인]` 후 진행)**:
- 새 기능·명령어·콘텐츠·아이템, 확률·수치·보상·경제 조정, 문구 톤·주간스쿼드 프롬프트 변경
- 이미 쌓인 시트 데이터 수정·삭제·이관(쓰기 코드 수정은 A, 기존 행 손대기는 B)
- 여러 사람에게 역할·DM·멘션을 한꺼번에 보내는 일, 공지 채널에 새 종류의 글
- 분석기 동작이 바뀌는 릴리스(버그 수정 릴리스는 A — 아래 제한)

**절대 금지**: 토큰·키 커밋, TLS·HTTPS_PROXY 손대기, 남의 커밋을 덮는 강제 푸시, 시트 탭 삭제, 킬스위치·MIN_ANALYZER_VERSION 우회,
후원 계좌 정보 변경, 커밋·주석·PR 에 모델 이름.

## 한 회차 절차
1. **동기화** — 두 저장소 `git fetch origin main` 후 작업 브랜치 `claude/project-cloud-migration-0qtorl` 를 main 으로 맞춘다
   (`git checkout -B claude/project-cloud-migration-0qtorl origin/main` — 브랜치에 main 에 없는 커밋이 있으면 버리지 말고 rebase).
   `log.md` 맨 위 회차와 `backlog.md` 를 읽는다.
2. **신호 수집** — `python3 tooling/improve/signals.py --since <지난 회차 epoch> --bot-src <main 의 bot.py> --version-file version.txt`.
   추가로 GitHub MCP 로 두 저장소의 최근 24시간 Actions 실패(`actions_list` list_workflow_runs, status completed → conclusion failure)를 본다.
   지난 회차 배포가 있었으면 그게 실제로 올라왔는지(`deployed: true`)와 그 뒤 새 오류가 늘지 않았는지 먼저 본다 — 아니면 그게 이번 회차 1순위.
3. **분류** — 새로 알게 된 것을 `backlog.md` 에 넣는다(중복이면 기존 항목 갱신). 항목마다: 등급(A/B)·근거·영향·상태.
   주 1회(일요일 회차)는 **발견 패스**도 돈다: Workflow 로 최근 7일 바뀐 코드(`git log --since`)를 영역별로 나눠 버그를 찾고
   반박 검증까지 거친 것만 backlog 에 넣는다. 사장님께 드릴 기능 아이디어(B)는 데이터 근거와 함께 한 주에 최대 2개.
4. **고르기** — 이번 회차에 배포할 것은 **최대 1건**: A등급 중 우선순위 최상위, 또는 `[승인]` 붙은 B 항목.
   할 게 없으면 5~7단계를 건너뛰고 8단계로.
5. **구현·검증** — 원인부터 확인(추측으로 고치지 않는다). 수정 뒤:
   - 문법: `python3 -m py_compile`, 봇은 가능하면 모듈 import 스모크(외부 의존 스텁)
   - 동작: 고친 경로를 실제로 실행하는 재현 스크립트(전투 쪽이면 CLAUDE.md 대로 장비·보스 3종·엄/비엄)
   - 독립 검토: Workflow 로 서로 다른 관점의 검토 에이전트 2개 이상 + 지적마다 반박 검증. 살아남은 지적은 고치고 다시 검증.
   - 웹이면 Playwright(`/opt/pw-browsers/chromium`)로 해당 화면을 띄워 본다.
6. **배포** — CLAUDE.md 대로: 브랜치 커밋 → main fast-forward(`git push origin HEAD:main`, 거부되면 rebase 후 재시도).
   - 웹 수정: `index.html` 의 `BUILD_ID` 올리기
   - 클랜원 눈에 보이는 변화: `data/patch_notes.json` 항목(클랜원 말투)
   - 분석기 릴리스(`analyzer-release.yml`, version = version.txt + 0.01): **하루 1회까지, 19:00~03:00 KST(내전 시간) 금지**
   - 배포 순서: 분석기·패치노트 → 릴리스 → 봇(봇은 bot.py 가 바뀔 때만 재시작하므로 마지막에 올려야 패치노트 공지가 바로 나간다)
7. **배포 확인·롤백** — 봇은 10분 안에 스스로 받아 재시작한다. 20분까지 `signals.py` 로 `deployed: true` 와 오류 증가 여부를 본다.
   - 20분 안에 안 올라오거나(`deployed: false`/응답 없음), 새 코드 위치에서 예외가 반복되면 **즉시 `git revert` 후 main 푸시**(자동 롤백)
     하고 log 에 사고로 적고 사장님께 알린다.
   - 분석기 릴리스는 워크플로 success + version.txt 올라감 확인.
8. **기록·보고** — `log.md` 맨 위에 회차 기록(아래 형식)을 넣고 backlog 상태를 갱신해 커밋·푸시(패치노트 없는 툴링 커밋은 main 직행 가능).
   사장님께는 **배포했거나 · 승인할 제안이 새로 생겼거나 · 사고/롤백이 있었을 때만** 한국어로 짧게(3~6줄) 보고한다. 아무 일 없으면 조용히 끝낸다.

## 회차 기록 형식(`log.md`)
```
## 2026-09-28 10:13 KST · epoch 1790550780
- 신호: 봇 배포 일치 · 새 오류 2(loc…) · 결과대기 고착 0 · 분석기 뒤처짐 3/12
- 배포: (없음) | [A] 제목 — 커밋 abc1234(봇)/def5678(분석기) · 확인 deployed ✓ · 오류 증가 없음
- 제안: B-7 새로 올림(사장님 승인 대기)
- 다음: …
```
`epoch` 는 다음 회차의 `--since` 로 쓴다.

## 예산·안전장치
- 한 회차 Workflow 는 에이전트 10개 이내. 한 회차 배포 1건. 같은 항목을 2회차 연속 실패하면 `막힘` 으로 두고 사장님께 묻는다.
- 봇 자체에도 안전장치가 있다: 새 bot.py 는 compile·import 검사 뒤 교체, 부팅 2회 실패 시 이전 버전으로 자동 롤백(`self_update`).
  이걸 믿고 대충 올리지 말 것 — 모듈은 뜨는데 기능이 깨지는 건 못 잡는다.
- 사장님이 채팅으로 방향을 바꾸면 그게 이 헌장보다 우선이다. 헌장 자체를 고쳐야 하면 backlog 에 B 로 올린다.
