### 1.1 사장님 문제의 원인 — 확정된 것과 아직 모르는 것
**확정(코드·실측)**
- `[실측]` 폰 크기 Chromium 에서 20초 플레이 → 화면 숨김 → `pause` 로 멈춤(정상) → 다시 보여도 `pause` 유지 → **새로고침하면 상태 `title`, S 객체 없음.** (R5 life.py, 검증이 재실행해 재현). 이것이 보여 주는 것은 "페이지가 다시 열리면 처음부터"라는 사실이다.
- `[코드]` `survivors.html` 은 visibilitychange(hidden)·blur 에서 `pauseGame()` 만 부르고(1144~1145행) 판 상태를 어디에도 저장하지 않는다. 판 저장·`pagehide`·`wasDiscarded` 코드 0건.

**확정(사장님 답변, 2026-10-08)**
- 사장님 폰은 **안드로이드**다(아이폰 아님).
- "웹 팝업창"은 **디스코드 앱 안에서 게임 링크를 눌렀을 때 뜨는 내부(내장) 브라우저 창**이다("게임링크는 디스코드 내부창이었던거같네"). 그 창은 다른 화면에 다녀오면 페이지를 지워 버려서 게임이 첫 화면(키아트)으로 돌아간다. 기억에 따른 답이고 스크린샷은 없으므로 안드로이드 표 A1·A2 가 한 번 더 확인한다.
- 위 두 사실을 합치면: 솔로는 판을 폰 메모리에만 들고 있는데 디스코드 내부창이 페이지를 지우므로 처음부터가 된다. 웹이라서 생기는 일이 아니다.

**아직 모르는 것**
- 그 내부창이 안드로이드의 어떤 종류인지(크롬 커스텀 탭 계열인지 웹뷰 계열인지, 기종·디스코드 버전에 따라 다른지)와 **왜 지우는지**(메모리·창 정책): 확인 못 함. 사장님 기종도 아직 모른다.
- 창이 지워져도 `localStorage` 가 남는지, 디스코드 승인(OAuth) 왕복 뒤 어디로 돌아오는지·로그인이 유지되는지, 메뉴에 "브라우저로 열기"가 있는지: 확인 못 함 → 안드로이드 표 A4~A6. 내부창이 `visibilitychange`(hidden)·`pagehide` 를 주는지는 표로는 가릴 수 없고, #12 이어하기 시험판을 사장님 폰의 내부창에서 눌러 보아야 안다.
- 아이폰에서 같은 일이 생기는지, 클랜원 중 아이폰 비율: 확인 못 함(D17·D20).

**철회된 가설 — 아이폰 홈 화면 앱의 "완료" 시트 (첫 개정의 1순위)**
첫 개정은 "자동 로그인 이동이 아이폰 홈 화면 앱에서 인앱 브라우저 시트(위에 "완료/Done" 막대)를 만든다"를 1순위로 올렸다. 사장님은 아이폰이 아니고 창이 디스코드 내부창이므로 **사장님 증상의 설명으로는 틀린 가설**이다. 다만 두 가지는 남는다.
- `[코드]` 사실은 그대로다: `survivors.html` 4~21행 머리 스크립트는 "한 번 로그인한 적이 있고(`sgg_dc_auto`) 토큰이 없거나 만료 24시간 안"이면 **페이지를 열자마자** `location.replace` 로 `discord.com`(`prompt=none`)에 가고, 돌아올 때 `index.html`(1,128,501바이트, 압축 전 `[실측]`)을 받은 뒤 `location.replace('survivors.html')`(index.html:9620, 399,772바이트)로 게임에 들어온다. 이 왕복이 **내부창 안에서** 문제를 더하는지는 확인 못 했다(A5 는 사람이 직접 하는 로그인 왕복만 묻는다 — 열자마자 가는 자동 이동은 2차 시험 12·13번을 안드로이드 내부창에서도 열어 확인한다).
- 아이폰 사용자에게 별개의 위험으로 남긴다: `[외부]` 아이폰 홈 화면 앱은 범위 밖 이동을 인앱 브라우저 시트로 열고 저장소를 공유하지 않는다는 보고(Firtman 2023-06; iOS 26 에서도 같은지 `[미확인]`), discord-api-docs 이슈 6160(아이폰 디스코드 인앱 브라우저에서 `prompt=none` 이 실패 창을 만든다는 2023 보고). 아이폰 표 4a·5번으로 지원자가 있을 때만 확인한다(§9.1-3).

**이 사실이 바꾸는 것**
- **레이드: 클랜원 대부분의 입장 경로는 디스코드 모집글 링크 → 내부창일 것으로 `[추정]`한다. 내부창을 1순위 환경으로 설계·시험한다**(§2.7·§3.3): 창이 지워질 수 있음(서버가 판을 들고 있고 같은 링크로 재입장), 내부창 안의 디스코드 로그인 왕복과 세션 유지, "브라우저로 열기" 안내, 초대 링크를 내부창이 연다는 가정. 레이드는 로그인을 레이드 원점에서 직접 하고 진행 중 방 복귀 때 디스코드로 가지 않는다(§2.6·§3.2).
- **솔로: "이어하기"(#12, 별도 작업·다른 에이전트 진행 중)가 바로 이 경우를 겨냥한다.** 저장 시점은 화면이 숨겨지는 순간(`visibilitychange` hidden·`pagehide`), 저장소는 `localStorage` 다(§11 S5). 창이 지워져도 `localStorage` 가 남는지는 안드로이드 표 A6 으로 확인하고, 내부창이 그 이벤트를 주는지는 #12 시험판을 내부창에서 눌러 확인한다 — 남지 않거나 이벤트가 안 오면 #12 에 알려 저장 방식을 다시 본다. 중복 구현 금지.
- **S1(홈 화면 앱화)의 미룸 근거가 바뀌었다**: 이전 이유(원인이 이것이라 증상이 늘 수 있음)는 사라졌다. 새 이유는 ① 클랜원 대부분이 디스코드 내부창으로 들어올 것이라는 `[추정]`(비율 모름)이라 홈 화면 앱의 이점(주소창 없는 전체화면·아이콘)이 일부에게만 닿고, ② 아이폰에서 별도 시트가 뜨는 위험이 미확인이라는 것이다. 그래서 S1 은 **우선순위를 낮추고** 아이폰 쪽은 지원자 확인 뒤로 둔다(§11).
- **S8(자동 로그인 이동 완화)** 은 이제 "가설 확인"이 아니라 안드로이드 표 A5(내부창에서 로그인 왕복 결과), 2차 시험 12·13번(안드로이드 내부창·아이폰) 또는 아이폰 표 4a 로 문제가 확인될 때 한다.

결론: 웹이라서가 아니라 **솔로가 판을 폰 메모리에만 들고 있는데 디스코드 내부창이 페이지를 지워서** 생긴다(확정). 레이드는 서버가 판을 들고 있어, 내부창이 지워져도 같은 링크로 다시 들어오면 같은 판에 붙는다(단 §7.4 의 15초 보호·45초 쓰러짐 규칙 안에서, 서버가 죽으면 판이 사라짐).

### 2.2 호스팅 — 레이드 서버를 어디에

**사실**
- `[실측]` 봇 주소 `hth3thmujs.apps.bot-hosting.cloud` = `178.105.112.237` → Falkenstein DE, Hetzner AS24940, 역DNS `…your-server.de` (ipinfo·ipwho.is, 검증이 재확인). 단 이것은 입구(Caddy 프록시) 위치이며 컨테이너 위치까지 확인한 것은 아니다.
- `[외부]` 서울↔프랑크푸르트 리전 간 지연 현재 표기 227.6ms, 서울↔도쿄 35.0ms, 서울↔오사카 25.0ms (economize.cloud, AWS 리전 간·왕복 표기 없음, 검증이 corrected). **폰→Hetzner 실측이 아니다.**

#### 2.3.2 서버 비용 규모 (정정 반영, 이번 개정에서 방 한도 재설계)
- R2 원 수치 "4인 30Hz = 코어 5%" 는 **초반 240초 값**이다(검증 corrected). 15분 전체 평균은 부하 3 상태에서 CPU 3.2ms/틱(벽시계 2.4ms) = 코어 약 **7~10%**, 후반(적 220마리 상한)은 더 높다 `[실측]`. 이 3.2ms 는 (a) 소유자 필터가 없어 풀이 액터 수만큼 중복 갱신되는 패치에서 잰 값(의미가 틀린 상태), (b) 스냅샷 인코딩·GC 를 **뺀** 값, (c) 부하 3 에서 잰 값이다.
- R1 의 "방 1개 7~23%, 3~8방/vCPU" 는 단일 플레이어 측정에 ×8(인원·적)·×2(느린 vCPU) 가정을 곱한 **추정**이다(검증 corrected). 측정은 LOW 모드(적 상한 140)였다.
- **옛 계획치(방당 코어 15~20%, vCPU 당 3방)와 한도(전역 방 12·연결 80)는 서로 모순이라 폐기한다.** 12방 × 15% = 180% 로 1 vCPU 에서 불가능하고, 이전 합격 기준 "8방 동시에서 틱 p99 < 33ms" 도 산술상 못 지킨다: 평균 3.2ms 로만 쳐도 8방 = 25.6ms / 33.3ms(코어의 약 77%)이고 인코딩·GC·후반 틱·기믹은 그 위에 얹힌다.
- **새 규칙**: 동시 전투 방 한도를 숫자 하나에서 유도한다 — `한도 = floor(0.6 × vCPU 수 ÷ 측정한 방당 코어 사용률(p95, 인코딩+GC 포함))`. 측정 전 임시 시작값은 **1 vCPU 에 동시 전투 3방(평균 가정 시 코어 약 29%), 로비 6방**. 1단계 실측으로 교정한다.
- **입장 제어(admission control)**: 서버가 이벤트 루프 지연 p99 와 방 틱 p99 를 계속 재서, 임계(제안: 루프 지연 p99 > 10ms 가 5초 지속)를 넘으면 **새 방 생성·시작을 거절**("서버가 바쁩니다, 잠시 뒤")하고 기존 방은 20Hz 폴백으로 버틴다. 한 대가 모든 방을 함께 무너뜨리는 대신 문 앞에서 막는다.
- 단일 스레드 한계와 한 방의 오류 전파는 **방당 worker_threads**로 푼다(§7.1).
- 기대 동시성: 클랜원 수십 명, 레이드는 약속을 잡고 하는 콘텐츠 → 동시 1~3방. 8방은 "과부하에서 거절·강등이 동작하고 프로세스가 죽지 않는가"를 보는 **스트레스 시험**으로만 둔다(합격 기준은 §4 G2').
- 틱 스파이크: 단일 플레이어 p99 가 1.4~11ms(부하 의존)라 4인에서는 한 틱(33ms) 근접 가능 `[추정]`. 고정 시간 단계 루프 + 틱 시간 계측 + 지연 시 15/20Hz 폴백을 설계에 넣는다. `/health` 에 틱 시간 max 도 기록한다.

### 2.4 프로토콜

- **전송**: WebSocket(wss), 바이너리 스냅샷 + JSON 제어 메시지. 순서 보장 TCP 이므로 직전 대비 델타를 쓸 수 있다(밀림 처리는 아래 "백프레셔"). 헤드오브라인 블로킹 위험은 §9. WebTransport/WebRTC 데이터채널은 Safari 지원 `[미확인]` 이라 쓰지 않는다.
- **틱**: 서버 시뮬 30Hz 고정 dt=1/30(원본 dt 상한 0.05 안, 하네스가 검증한 영역). 스냅샷 15Hz(2틱마다). 입력 15~30Hz. 서버 루프는 hrtime 누적기, 따라잡기 최대 3틱. 폴백 20/10Hz.
- **입력(C→S)**: `{seq u16, 방향 각도+세기 2B, 버튼 1B}`. 서버가 벡터 크기를 1로 제한(속도 위조 방지). 서버는 플레이어마다 **마지막으로 처리한 입력 seq(`ack_seq`)** 를 기억한다.
- **스냅샷(S→C)**: 적은 활성 슬롯 비트맵 + 마리당 dx,dy int8 + hp/플래그 = 마리당 약 3B(델타) / 7B(전체). 플레이어 4명 각 8B(+본인은 정밀 10B + **`ack_seq`**), 보스 약 20B. `[추정]` 클라당 다운 10~35KB/s — 이 산식은 **적·플레이어·보스만** 센 것이다. 부메랑·펫·궤도·훅·광선 등 13개 풀의 상태, 위험 표시(telegraph), 월드 싱글톤(`cone/cardW/room/ebooms/beams`)은 아직 안 셌으므로 하한이다 `[미확인]`. 스냅샷에 무엇이 들어가는지는 §5 E10 의 "필드 추출"로 먼저 확정한다(draw 가 적 하나당 25개 안팎의 필드를 읽는다 `[코드]` 2612~3269행).
- **이벤트**: 투사체 생성(종류·시작점·각도·속도·수명), 폭발, 피격 숫자, 소리, 배너는 상태가 아니라 이벤트로 별도 전송(1~3KB/s `[추정]`). "투사체는 직선이라 클라가 진행"은 직선 무기에만 맞다 — 39종을 **직선 / 추적·궤도 / 지속 구역**으로 분류해 앞의 둘 중 상태 동기화가 필요한 것을 가려내는 것이 1B 첫 작업이다. 서버 스텁이 `AU/EX/txt/banner/taunt/say` 호출(약 145곳)을 이벤트 큐로 바꾼다 — Proxy 한 겹.
- **본인 이동(예측 + 재생 보정)** — 이전 판의 "서버와 8px 이상 다르면 스냅"은 상시 고무줄이 되므로 폐기:
  1. 클라가 입력을 즉시 적용하고 **입력 이력(최대 1초분)** 을 `seq` 와 함께 보관한다.
  2. 서버 스냅샷의 본인 상태와 `ack_seq` 를 받으면, 서버 상태에서 출발해 `ack_seq` 이후의 보관 입력을 **같은 dt 로 다시 적용(replay)** 해 예측 위치를 재계산한다.
  3. 재계산 위치와 현재 표시 위치의 차가 4px 이하면 무시, 4~64px 면 100ms 에 걸쳐 부드럽게, 64px 초과면 스냅. 서버가 끌림·기절·감옥 같은 **강제 이동**을 `forced` 로 알리면 즉시 적용한다. (임계값은 제안, 시험으로 조정)
  4. 근거 `[추정]`: RTT 60ms 에서 입력이 스냅샷에 반영돼 돌아오기까지 약 100ms(상행 30 + 틱 대기 평균 16 + 스냅샷 대기 평균 33 + 하행 30). 속도 180px/s 면 재생 없이 비교할 때 이동 중 상시 약 18px 어긋나 8px 임계를 계속 넘는다.
- **타인·적 보간(적응형)**: 고정 100~130ms 를 폐기하고, 스냅샷 도착 간격의 지터를 재서 **스냅샷 2~3개분(하한 100ms, 상한 250ms)** 뒤 시점을 그린다. 한 프레임에 스냅샷이 3개 이상 몰려 도착하면(멈췄다 터지는 stall-then-burst) 보간 버퍼를 버리고 최신으로 이동하며, 500ms 넘게 묵은 이벤트는 소리·숫자를 생략하고 상태만 반영한다. 외삽은 150ms 까지만 하고 그 뒤엔 정지시킨다.
- **피해 판정과 지연**: 판정은 서버 위치 기준이다. 모든 위험 기술은 **예고 ≥ 0.8초**(기믹 3초 이상 권장)를 두어 지연 보상을 대신하고, 예고 종료 순간의 피격 판정은 플레이어의 **최근 150ms 위치 이력 중 하나라도 범위 밖이면 회피로 본다**(피하는 쪽에 유리, 제안 — 3단계 봇·사람 시험으로 검증). 지터·300~1000ms 정지를 주입하는 시험을 둔다(§4 1단계).
- **백프레셔(느린 수신자)**: 서버는 클라별 `ws.bufferedAmount` 를 본다. 스냅샷 2개분을 넘으면 그 클라에게는 이번 스냅샷을 **건너뛰고** `needFull` 표시 → 버퍼가 비면 풀 스냅샷을 보낸다. 델타는 항상 **그 클라에게 실제로 보낸 마지막 상태** 기준으로 만든다(건너뛴 프레임이 있어도 양자화 오차가 쌓이지 않게). 256KB 를 넘으면 4005 로 닫는다. 느린 수신자 시험을 1단계 합격 기준에 둔다.
- **하트비트(응용 수준)**: 브라우저는 JS 가 멈춘 탭에서도 WebSocket **프로토콜 ping 에는 대신 응답**하므로(데스크톱·안드로이드 백그라운드 탭 `[추정·미확인]`) 프로토콜 ping 은 "죽은 소켓 감지"에만 쓴다(5초 주기, 10초 무응답이면 닫기). **자리비움 판정은 응용 메시지로 한다**: 클라 JS 가 1초마다 입력(없으면 `hb`)을 보내고, 화면이 숨겨질 때(`visibilitychange` hidden·`pagehide`·`freeze`) **최선 노력으로 `{t:'bg'}` 를 한 번 보낸다**(실패해도 무해). 서버 판정은 §7.4. 클라는 보이는 상태에서 3~4초 무수신이면 스스로 소켓을 닫고 재접속한다.
- **버전**: `hello{proto, build, ticket|session_key|resume_token}`. `proto` = 전송 규격·스냅샷 스키마 정수, `build` = 시뮬 콘텐츠 해시(번들 해시). 파일 해시와 시뮬 해시를 구분한다. 클라와 서버는 **같은 번들**에서 나오므로(§2.6) 불일치는 "오래 열려 있던 탭"에서만 난다.
- **close 코드와 클라 행동**

### 2.6 클라이언트 배포 구조 — 레이드 번들은 레이드 서버가 준다 (이번 개정의 핵심)

**문제 (검토 C2 blocker · C3)**: 이전 설계는 클라이언트가 GitHub Pages 의 `survivors.html`(솔로와 같은 파일)이고 서버가 "같은 시뮬 해시"를 요구했다. 그런데 `[실측: git log]` `survivors.html` 은 9/28 이후 59커밋(하루 최대 16~19), Pages 는 즉시 배포되고(캐시 약 10분 `[추정]`), 레이드 서버는 방 0개일 때만 교체(최대 25분 대기)한다. `survivors.html` 에는 `BUILD_ID` 가 **없다**(0건 `[코드]`; `index.html` 에만 11건) → 불일치 시 "BUILD_ID 로 새로고침"이 존재하지 않는 경로다. 아이폰이 페이지를 버린 뒤 다시 여는 것이 핵심 시나리오인데 그때 새 클라 + 옛 서버가 4002 에 막히고, 서버를 롤백하면 새 클라가 계속 붙지 못한다. 또 로그인 왕복이 모집글 쿼리를 버린다 — `survivors.html` 16·436행이 `sgg_oauth_return` 을 고정값 `'게임:survivors'` 로 쓰고 `index.html:9620` 이 `survivors.html` 로만 되돌린다 `[코드]`.

**결정**
1. **레이드 번들** = CI 가 **고정(pin)한 커밋**의 `survivors.html` 에서 `<script>` 본문을 뽑아 (a) 서버용 `sim.js`, (b) 브라우저용 `index.html`(레이드 껍데기 + 같은 script)로 조립한 산출물. 서버가 해시 이름 경로 `/b/<해시>/`(immutable 캐시)로 제공하고, 진입 `/`(no-cache)가 현재 번들로 보낸다.
2. **pin**: `raid/PIN` 한 줄(커밋 sha). 에이전트가 의도적으로 올릴 때만 바뀐다. 올릴 때 게이트: Node 로드 + 4액터 900초 + ESLint `no-undef` + 골든 해시 + 밸런스 시뮬 재실행(편차 보고). 솔로의 잦은 수정은 pin 을 올리기 전까지 레이드에 영향이 없다 → 솔로 무기 조정이 레이드 보스 체력 보정을 조용히 바꾸는 표류도 막는다(검토 C3).
3. **서버 이미지 = 서버 코드 + 번들(현재 + 이전 1개)**. 롤백은 이미지를 되돌리면 클라도 같이 돌아간다. 진행 중 방은 자기 `build` 로 끝까지 간다(드레인).
4. **로그인은 레이드 원점에서 직접**: 디스코드 implicit OAuth. 디스코드 개발자 페이지에 레이드 원점 복귀 주소를 **추가 등록**한다(사장님, §10 D10; 지금 등록된 것은 메인 페이지뿐 — `survivors.html:433` 주석). `state` 에 방 코드(`[A-Z2-9]{6}` 검증)를 실어 왕복시켜 모집글 링크가 로그인 뒤에도 살아남는다. 토큰 → 봇 `POST /party/ticket`(봇 CORS 에 레이드 원점 추가: 지금은 `/p6/`·`/nv/` 만 단일 `P6_ORIGIN` 고정, 프리플라이트는 그 밖에 `*` — `[코드]` bot.py 17014·17321·17463행 → `/party/` 한정 허용 목록 필요) → 입장권 → 레이드 서버가 **세션 키**(256비트, 서버는 sha256 만 보관, 7일, 쓸 때마다 회전, 서버가 폐기 가능)를 발급 → 이후 입장·복귀는 `hello{session_key}` 로 **디스코드·봇 호출 없이**. 위험(장기 열쇠 탈취): 7일·회전·폐기 가능·보상은 결과 접수 때 봇이 클랜원 여부를 다시 확인(`_nv_member`)·일일 상한으로 줄인다.
5. 솔로 `survivors.html` 에는 레이드 원점으로 가는 **링크 버튼**만 추가한다. 솔로 PWA(S1)와 레이드 PWA 는 **원점이 달라 별개의 앱**이다(manifest 는 레이드 원점에, `scope=/`).
6. **잃는 것**: 레이드 원점에서 디스코드 로그인을 한 번 더(저장소가 원점별), 도메인 필수, 솔로 개선이 레이드에 자동 반영되지 않음(pin 올림 필요), 번들 조립 CI.
7. 기각: (a) Pages 의 `survivors.html` 이 레이드 스크립트를 교차 원점으로 불러오기 — 껍데기 DOM·쿼리 유실이 그대로 남고 pin 의 이점이 반감. (b) 서버가 옛 Pages 파일을 요구하며 해시 협상 — Pages 는 옛 버전을 주지 않는다.
8. 시험: 버전 불일치 매트릭스(옛 서버 + 새 번들 요청 / 새 서버 + 옛 탭 / 롤백 뒤 접속), 4002 처리가 무한 새로고침을 하지 않는지.

### 2.7 레이드 진입 화면과 초대 링크 — 디스코드 내부창이 1순위 환경 (검토 C1·C3, 2차 개정)
- **확정(사장님 답변)은 게임 링크**: 안드로이드에서 흐접새우 링크는 **디스코드 앱 안의 내부창**으로 열린다(§1.1). 모집글 링크도 같은 방식으로 열릴 것으로 **가정**한다(디스코드에 올라가는 글이라는 이유. 레이드가 만들어진 뒤 3차 시험에서 모집글 링크로 확인). `[외부]` 아이폰에서도 모집글 링크는 설치된 홈 화면 앱을 열지 **않고** 디스코드 인앱 브라우저나 사파리로 열린다는 포럼 보고(공식 문서는 못 찾음). 즉 "PWA 설치로 불편을 푼다"는 약속은 **초대 링크 진입에는 적용되지 않으며**, 클랜원 대부분의 입장 경로는 내부창일 것으로 `[추정]`한다(PC 로 들어오는 비율도 모름). 홈 화면 앱은 일부 사용자의 보조 경로다.
- **내부창 설계 요구 5가지와 시험**
  1. **폐기는 정상 상황이다.** 창이 지워져도 판은 서버에 남고, 같은 링크(또는 방 코드)로 다시 들어오면 같은 uid 의 좌석을 되찾는다(§7.4). 시험: Chromium 에서 `page.close()` 후 **새 page** 로 같은 방에 재접속하되 (a) 같은 BrowserContext(저장소 유지)와 (b) **새 BrowserContext(저장소 비움 = 세션 키 없음 → 입장권 경로)** 둘 다 통과, 복귀 소요가 15초/45초 창 안인지 기록. 실제 내부창의 정책은 에뮬이 재현하지 못하므로 합격 근거는 안드로이드 표 A2·A3 이다.
  2. **내부창 안의 디스코드 로그인(OAuth) 왕복.** 승인 화면을 다녀온 뒤 같은 창에서 레이드 원점으로 돌아오는지, 내부창이 디스코드 앱 로그인과 별개 세션이라 승인 화면에서 다시 로그인해야 하는지: 확인 못 함 → A5. 모집글의 방 코드는 `state` 로 왕복시킨다(§2.6-4). 시험: 가짜 승인 페이지로 `state` 왕복(§4 2단계).
  3. **세션 유지.** 세션 키는 `localStorage` 에 두되(`try/catch`), 내부창이 저장소를 지우는 쪽이 **기본 가정**이어도 동작해야 한다 — 지워지면 입장권(로그인)으로 들어오고 같은 uid 좌석을 되찾는다. 내부창이 저장소를 남기는지: 확인 못 함 → A6.
  4. **"브라우저로 열기" 안내.** 안드로이드 내부창은 UA 로 구별되지 않을 수 있다(`[미확인]` — 아이폰 인앱도 UA 로 감지되는지 미확인, 2차 시험 페이지가 UA 를 화면에 찍는다). 구별되면 배너를 먼저 보여 주고, 구별되지 않으면 감지에 의존하지 않는 상시 안내(첫 화면·결과 화면의 작은 문구 "화면이 초기화되면 같은 링크를 다시 누르세요, 판은 서버에 남아 있습니다")를 쓴다. 메뉴 이름은 안드로이드 표 A4 에 사장님이 적은 이름을 그대로 쓴다.
  5. **초대 링크를 내부창이 연다고 가정.** 링크의 방 코드가 내부창을 거쳐도 살아남는지는 실제 모집글 링크로 2차 시험 때 확인한다(A1 은 지금 게임 링크로 하는 확인).
- 레이드 원점 첫 화면: `[내 파티 이어하기]`(저장된 방이 있을 때) · `[방 코드 입력]` · `[새 방 만들기]`. 홈 화면 앱에서는 이 화면이 시작점이다.
- 모집글 문구: 링크와 함께 "홈 화면 앱으로 열려면 앱을 켜고 코드 `ABC123` 을 입력하세요"를 싣는다.
- 인앱 브라우저·사파리·홈 화면 앱은 저장소가 서로 달라 맥락마다 세션 키가 따로다. 세션 키가 없는 새 맥락은 로그인(입장권)으로 들어오되, **같은 uid 가 진행 중 방에 좌석을 갖고 있으면 입장권 입장도 그 좌석을 되찾고 옛 소켓에 4001 을 보낸다**(§7.4). 4001 을 받은 쪽은 자동 재접속을 멈추므로 서로 밀어내는 싸움이 없다.

### 3.2 로그인
- `[코드]` 현재 디스코드 implicit OAuth(`response_type=token`), 토큰은 해시로 돌아와 `localStorage.sgg_dc`(7일). 만료 24시간 전에는 같은 창을 `discord.com` 으로 보내는 `prompt=none` 자동 갱신(`survivors.html` 4~21행 머리 스크립트, `index.html` 34~61행). 복귀는 메인 페이지(index)로 와서 `sessionStorage` 의 `sgg_oauth_return` 으로 게임에 되돌린다. 이 구조는 **쿼리를 버리고**(`'게임:survivors'` 고정) 복귀 때 페이지를 두 번(index 1.1MB → survivors 400KB) 받는다.
- `[외부]` 아이폰 홈 화면 앱은 사파리와 저장소가 분리되고(WebKit 181849 "by design"), 범위 밖 링크는 인앱 브라우저로 열려 저장소를 공유하지 않는다(Firtman, 2023-06 — iOS 26 반영 `[미확인]`). OAuth 복귀가 PWA 로 안 돌아오는 포럼 보고가 다수(Apple 포럼 810832 등). **디스코드 흐름이 실제로 어떻게 되는지는 아무도 확인 못 했다.** 사장님 안드로이드의 디스코드 내부창 안에서 승인 왕복이 어떻게 되는지도 확인 못 했다(A5).
- iOS 26 은 홈 화면에 추가한 모든 사이트를 기본 웹앱으로 연다(WebKit 16993, 끄는 스위치 있음) → 이미 `survivors.html` 을 추가한 클랜원은 지금 standalone 으로 열리며 로그인이 깨졌을 수 있다 `[미확인]`.
- **설계(이번 개정)**: 레이드는 위 구조를 **쓰지 않는다**.
  1. 레이드 원점이 자기 로그인 화면을 가진다(§2.6-4). 복귀 주소는 레이드 원점의 한 페이지이고 `state` 에 방 코드를 싣는다. 그 페이지는 토큰을 봇에 올려 입장권을 받고, 서버에서 세션 키를 받으면 토큰을 지운다.
  2. 이후 입장·재접속은 세션 키(7일, 회전). **진행 중 방 복귀 때는 디스코드로 가지 않는다**(머리 스크립트식 자동 이동 없음). 세션 키가 만료됐으면 방에 붙지 못하므로, 만료 하루 전부터 판이 **끝난 화면(결과·로비)에서만** 조용히 갱신한다.
  3. 안드로이드 표 A5(내부창) 또는 아이폰 표 5번(홈 화면 앱) 결과가 "디스코드 승인 뒤 앱·창으로 안 돌아온다"이면 **중계 로그인**: 앱이 랜덤 `state` + 짧은 확인 코드를 만들고 → 디스코드 승인 창 → 도착 페이지가 토큰+state 를 봇에 올리고 → 봇이 uid 를 검증해 장기 키를 발급 → 앱이 state 로 폴링해 받는다. 로그인 고정 공격 방지로 두 화면에 같은 확인 코드를 보여 준다. 대안: 봇 슬래시 명령으로 6자리 코드 입력.
  4. 시험: **"세션 키 만료 임박 + 페이지 폐기(새로고침) → 45초 안에 같은 좌석 복귀"** 를 CDP 네트워크 스로틀(Slow 4G) 아래에서 재고 소요를 기록한다(§4 2단계).

### 3.3 실기기에서만 보이는 위험 (자동 시험이 못 보는 것)
샌드박스에는 Playwright Chromium 만 있다. 아래는 `PHONE_CHECKLIST.md` 로 넘긴다 — **1부 안드로이드(사장님)가 기본, 2부 아이폰은 지원자가 있을 때만.** Chromium 에뮬로 대신 볼 수 있는 부분(`page.close()` 후 새 page 재접속, 새 BrowserContext, 가짜 승인 왕복, CDP frozen/offline)은 에뮬로 시험하고, 에뮬은 합격 근거가 아니라 회귀 감시다.
1. **(안드로이드·1순위) 디스코드 내부창**: 창 종류, 다른 화면·다른 앱에 다녀온 뒤 폐기 여부, 저장소 유지, 승인 왕복 뒤 복귀 위치, "브라우저로 열기" 메뉴, 뒤로가기 제스처(A1~A8). 아이폰의 홈 화면 앱은 로그인 복귀 위치와 로그인 유지, **앱 실행 직후 위에 완료/Done 막대가 있는 시트가 뜨는지**(아이폰 표 4a·5, 사장님 증상과는 별개 위험).
2. 앱 전환·화면 잠금 뒤 WS `readyState`·`onclose` 동작과 재접속 시간 — **소켓 생존 시험 페이지로 측정**(안드로이드는 사장님 폰의 디스코드 내부창에서, 아이폰은 지원자; 7.4 의 모든 수치가 이 값에 달려 있다).
3. 오디오 인터럽트 복구, 무음 스위치, 디스코드 음성을 켠 채의 소리.
4. 노치/다이내믹 아일랜드 안전영역, `100vh` 가 아래를 가리는지(아이폰 주소창 접힘 높이 함정은 일반 지식이며 출처 확인 못 함).
5. 가장자리 스와이프 뒤로가기·시스템 제스처 충돌, 두 손가락 조작, 핀치/더블탭 확대.
6. 메모리 부족으로 페이지가 버려지는 빈도, 저전력 모드 성능, 오래된 아이폰 캔버스 메모리(캔버스 1개 16.8Mpx, 전체 224~384MB 보고 `[외부]` — 우리 메인 캔버스 약 1.4Mpx·5.7MB, 협곡 바닥 캐시 상한 약 64MB(코드 상한, 서버 레이드에서는 쓰지 않을 수도 있음)), **15분 레이드 장면 뒤 발열·배터리·버벅임**.
7. 디스코드 인앱 브라우저의 동작(안드로이드는 1번에서 다룬다, 아이폰은 지원자), UA 로 감지하는 방법 `[미확인]`, 그 안에서 링크 → 로그인 → 입장 → 홈 → 복귀.
8. WebSocket 이 백그라운드에서 몇 초 뒤 닫히는지(안드로이드 내부창·iOS 모두 정확치 `[미확인]`; iOS 는 포럼 보고뿐) — 2번과 함께 G5.
9. 웹 푸시, 진동, 방향 잠금(안 되는 것이 정상이지만 확인).
10. 대기방에서 손 안 대고 2분 두면 화면이 꺼지고 좌석이 유지되는지(Wake Lock 폴백 포함).

### 3.4 성능 예산 (상대 게이트로 개정)
- `[실측]` 모바일 에뮬(412×860@2x, 캔버스 1.42Mpx) update 중앙값 0.2~0.9ms vs draw 5~20ms(적 30→140마리, CPU 스로틀 4~6x 에서 21~26ms) — **프레임의 95% 이상이 그리기**(검증이 load 13.7 에서 재현). 실행 간 편차가 2배라 합격 판정에 쓰지 않는다. 폰 프로필이 데스크톱 대비 draw 2~2.5배.
- 주의: `tests/survivors_perf_cmp.py` 방식은 동기 `update+draw` 를 한 프레임씩 호출해 **메인 스레드의 명령 기록 시간**만 본다. GPU 래스터·합성은 빠진다 → 에뮬 값은 승격/합격 근거가 아니라 **회귀 감시**용이다.
- 이전 판의 "레이드는 클라 엔티티가 솔로 호드(140+)보다 적다"는 플레이어 4명의 무기 풀(부메랑·펫·훅·궤도 등 13개 풀)과 동료 이펙트 재생을 세지 않은 가정이었다. 이전 "렌더 프레임 ≤24ms 평균"(약 41fps)은 위 실측과 거의 같아 의미가 없어 폐기한다.
- **새 게이트(1단계 합격 기준에 포함)**:
  1. 같은 기계·같은 부하에서 **(솔로 기준선) 대비 (4인 거울 상태 클라)의 update+draw 시간 비 ≤ 1.6배**(제안).
  2. 폰 프로필(412×860@2x, CDP CPU 4배)로 **15분 고정 시나리오**를 돌려 프레임 시간 p95 와 JS 힙(CDP `Performance.getMetrics` 의 `JSHeapUsedSize`)을 기록하고, 힙이 시간에 따라 증가하는 추세(누수)가 없는지 본다. 메모리 예산: 메인 캔버스 ≤ 3Mpx, JS 힙 추세 평탄.
  3. 실기기(안드로이드 사장님 폰, 아이폰은 지원자가 있을 때): 15분 레이드 장면 뒤 발열·배터리 감소량·버벅임(확인표 2차·3차). 최종 판단은 실기기 30fps 기준(승격 조건)과 함께 한다 — 에뮬 값은 합격 근거가 아니다.
- Canvas2D 로 시작. 승격 조건(제안): 중급 안드로이드·구형 아이폰 실기기에서 레이드 실전 장면이 30fps 아래로 5초 이상이면 해당 층만 WebGL. 먼저 쓸 값싼 수단: DPR 상한 1.5, 프레임 시간 감시 자동 하향, 네트워크 틱과 렌더 분리.
- 네트워크 예산(제안, 한 곳으로 통일): 클라 다운 **평균 ≤ 20KB/s, 피크 ≤ 40KB/s**(측정 단위: 1초 이동 평균). §2.4 의 10~35KB/s 는 하한 산식이다.

### 3.5 4인 HUD·터치 UI 명세 (검토 C1 — 1단계 전에 와이어프레임 확정)
`[코드]` 시야는 기기마다 다르다: `survivors.html` 231~235행 공식대로 폰 세로 390×844 는 월드 약 557×1206(SC 하한 0.7), PC 1920×1080 은 약 1491×838. 아레나 지름 1520·증언대 반지름 520 이라 폰에서는 한 화면에 동서 증언대가 같이 안 들어온다. 그러므로 **레이드 전용 서버 상수로 시야를 정하고**(E6), 화면 밖 대상은 화살표·미니맵으로 보여 준다.

- Node `ws` 서버(방당 worker, 입장권 없는 개발용 토큰), 방당 vm 컨텍스트(**판마다 새 컨텍스트** — 10/8 커밋 828d35a 가 "판을 연달아 할 때 풀 재사용 적의 이전 판 표식"을 고친 만큼 `newRun` 은 완전한 초기화가 아니다), 30Hz 루프+15Hz 스냅샷, 입력 수신, 백프레셔·입장 제어.
- 클라 레이드 모드: 서버 상태 거울 `S` + 액터별 빌드 거울, 본인 예측 + 재생 보정, 타인·적 적응형 보간, 이벤트 재생(소리·이펙트). **E10 은 무기 2종 시제품으로 먼저 점검 B 를 통과한 뒤 나머지를 한다.**

합격 기준 (자동)
- (a) 솔로 회귀 게이트 전부, 확장 골든 해시 일치, 하네스 별칭 유지.
- (b) Node 4액터 900초 × 5조합 예외 0 + ESLint `no-undef` 0 + 39무기 커버리지 39/39. 같은 시드의 새 컨텍스트와 두 번째 판의 해시가 같다.
- (c) 소유자 불변식: 같은 무기를 1인/4인으로 돌렸을 때 부메랑·로켓·펫·훅의 이동·피해가 소유자당 동일(중복 갱신 0), 킬 합계 = 월드 kills. **RNG 호출 순서가 인원에 따라 달라지므로 소유자별 RNG 스트림(E9)** 을 쓰거나 허용오차 기반으로 비교한다 — 정확 일치를 요구하지 않는다. `lastBlock`·`feed*`·`aura*` 계열 포함.
- (d) Playwright Chromium 2페이지: 두 클라가 같은 적을 보간 오차 허용치 안에서 같은 위치로 봄, 본인 위치 지연 0프레임(예측 + 재생), **지터·정지 주입 프록시**(300~1000ms 멈췄다 한꺼번에 전달 — TCP/WebSocket 에서 "손실률 5%"는 의미가 없어 이전 항목 폐기)에서 보정 스냅 한도 이내, 소켓 강제 종료 후 5초 안 재접속해 같은 캐릭터·판 복귀, 클라당 다운 평균 ≤ 20KB/s·피크 ≤ 40KB/s, **느린 수신자**(버퍼 한도 → 건너뛰기 → 풀 스냅샷 복구) 시험.
- (e) 클라 성능 게이트(§3.4) — 솔로 기준선 대비 비율, 폰 프로필 15분 힙 추세.
- (f) 격리·입장 제어: 한 방에서 의도적 무한 루프/NaN·Infinity/메모리 폭주 → 다른 방 무영향, 부모가 2초 안에 그 방 worker 종료, 8방 스트레스에서 입장 제어가 거절·강등하고 프로세스가 죽지 않음.
- (g) CDP 수명주기: `Page.setWebLifecycleState`(frozen/active)와 네트워크 오프라인 토글로 타이머 지연 조건에서도 재접속 상태기계가 동작 `[미확인: 기능 존재는 알지만 이 샌드박스에서 직접 확인 못 함 — 1B 첫 확인]`.
사장님이 할 일: 없음(서버가 아직 개발용). 시험 클랜원 구하기는 알파부터.
솔로 회귀: 위 (a)가 이 단계의 1번 게이트.

### 2단계 — 파티 로비·초대·재접속·방장 이탈  (규모 M, 약 4~5세션)
근거: 코덱은 `ws` 라이브러리가 있어 R4 의 150줄 Python 코덱이 필요 없다. 상태기계·입장권·세션 키·결과 API·레이드 원점 로그인이 일.

작업
- 레이드 서버: 방 상태기계(lobby→countdown→playing→ended→closed), 방 코드 6자(헷갈리는 글자 제외 31자), 좌석, 준비, 캐릭터 선택(중복 불가), 방장 전환, 1인 1방, 한 uid 의 소켓은 1개(새 연결이 옛 연결을 4001 로 대체, **같은 uid 의 새 입장은 기존 좌석을 되찾는다**), 세션 키·`resume_token`(128비트, 서버는 sha256 만 보관), 청소 태스크, `/health`, 번들 제공(§2.6).

합격 기준 (자동)
- aiohttp(또는 `ws`) 가짜 클라 4개: 생성→합류×3→준비→시작→30초 입력→종료→결과 1회 지급(멱등).

## 6. 레이드 MVP 명세 — 「또뀨의 진실의 방: 재판 레이드」

**R3 기획 기반, 독립 검증 없음. 아래 수치는 모두 초안이며 3단계 시험으로 조정한다.** 새 대사는 사장님 승인 전까지 "초안", 기존 코드 대사만 쓰면 승인 불필요. 이번 개정에서 **MVP 를 줄였다**(역할 버튼 2종·협동 기믹 2종, §4 3단계). 표의 "MVP" 열이 ✔ 인 것만 3단계에 들어가고 나머지는 4단계 이후 또는 점검 C 결과로 정한다.

### 6.1 왜 또뀨인가
`[코드]` `BOSS.ddo`(반경 46, 속도 56, hp 1300(기본, `bossMul` 로 스케일), atk `room`,`shots`)와 진실의 방(감옥)·`sp0/hit/dead/win` 대사가 이미 있다. 디스코드 월드보스로 친숙하고, 분산·감옥 구출·순서 맞추기가 개그("해명", "회의록", "딱 3시간")와 맞는다. 한 판 약 12~13분, 2페이즈, 15분 초과 시 "회의 시간 초과" 패배.
이름은 기존 디스코드 월드보스("공격" 채팅, 전설 드롭, `RAID_BOSSES`)와 겹치지 않게 **"파티 레이드"/"재판 레이드"** 로 한다.

### 6.2 조작과 역할
- 고유 무기는 지금처럼 **자동 발사**. 손가락은 이동 + **역할 버튼 1개**(자동 사용 기본 ON, 수동으로 맞추면 효과 +15%). 한 손 플레이 가능. HUD·엄지 영역은 §3.5.
- 능력치 표준화(솔로 해금·진행도·장비는 전투력에 영향 없음): 표준 HP 300(탱커 390), 속도 180. 방어 고정값은 비율로 환산(arm1/2/3 = 받는 피해 -3/-6/-9%, E15). 피해 단위는 "표준 HP 300 대비 %".
- 무기 성장은 카드 없이 시간 기준: 고유 무기 Lv3 시작, 2분마다 +1, 10분 Lv8, 2페이즈 시작에 각성 자동. 페이즈 시작에 공용 무기 1/유물 1 8초 선택(비정지).
- 역할 버튼(쿨타임 초안, MVP ✔ = 탱커·서포터만): 탱커 ✔ [도발 외침] 18초(4초 우선 표적+받는 피해 -50%) / 서포터 ✔ [응원] 18초(반경 200 아군 HP +30%, 2초 보호막, 소생 ×1.5) / 제어 [속박] 16초(반경 잡몹 2초 기절, 보스 경직 게이지 +15%) / 딜러 [몰아치기] 25초(5초간 피해 +35%, 경직 중 ×1.5). MVP 에서 제어·딜러는 버튼 없이 고유 무기만 쓴다.
- 17명 배정(R3, 코드 기준): 탱커 3(ddmj·yj·tw) / 서포터 3(ssu·amd·kyo) / 제어 5(sr·ddo·eom·hrb·bgb) / 딜러 6(jjg·ildj·brj·psg·mms·yumi). 같은 캐릭터 중복 불가(주간 특별 룰만 허용).
- **캐릭터 해금 정책 변경(검토 C3)**: 이전 판은 "해금 + 주간 대여 2명 + 상점 캐릭터 제외"였다. 그러나 `[코드]` 탱커 3명은 모두 보스 처치(ddmj 최종·tw 40분·yj 50분) 해금, 서포터는 공용 무기 Lv5·처치 1000 등 해금(survivors.html 526~540행)이라 순위표 기준 60분 클리어 5명뿐인 클랜에서 **균형 파티를 만들 수 있는 사람이 거의 없고**, 입장권 {uid,name,exp,jti} 에는 해금 정보가 없으며 봇은 `/p6/run` 의 `unlocks` 를 **클라이언트가 보고한 값 그대로**(허용 키 필터만) 쌓는다(bot.py 16881행). 능력치를 표준화했으므로 해금으로 막을 밸런스 이유도 없다. → **MVP 는 해금과 상관없이 17명 전원 선택 가능**(D5 변경). 상점 캐릭터(yumi·eom)의 후원 가치는 외형·칭호로 보호한다. 해금을 유지해야 한다면 봇이 입장권에 해금 목록을 넣는 설계가 필요하며 그 값이 클라이언트 보고라는 한계를 같이 적어야 한다.

## 7. 서버·세션·운영 설계

### 7.1 프로세스
- **부모 프로세스**: Node 22 + `ws`. 소켓·로비·입장 제어·번들 제공(§2.6)·`/health` 만 맡고 **시뮬 코드를 직접 돌리지 않는다.**
- **방당 `worker_threads` 1개**: 워커 안에 vm 컨텍스트(스파이크로 8개 228ms·+6.8MB `[실측]`) 하나가 시뮬을 돈다(판마다 새 컨텍스트). `resourceLimits.maxOldGenerationSizeMb` 로 방마다 힙을 제한하고, 부모↔워커는 `MessagePort`(입력·스냅샷은 transferable `ArrayBuffer`)로 주고받는다 `[추정: 구현 세부는 1B 첫 주에 스파이크로 확인]`. 워커는 틱마다 부모에 하트비트를 보내고, **2초 무응답이면 부모가 그 워커만 `terminate`** 하고 방을 종료한다(보상 없음, 알림). 워커의 예외·메모리 초과 이벤트도 그 방만 끝낸다.
- **왜 틱마다 `vm` timeout 이 아닌가** `[실측, 이 샌드박스 load 5~7, 상대 비교]`: 빈 `tick()` 호출 20,000회에서 timeout 옵션이 없으면 호출당 약 3µs, 있으면 약 515~828µs(수백 배), 50ms 제한에서 **정상 호출 7회가 오탐으로 중단**됐다(호출 하나가 CPU 를 못 받아 162~168ms 걸린 경우). 무한 루프는 51ms 에 끊겼다. 즉 timeout 은 벽시계 기준이라 부하가 높은 호스트에서 멀쩡한 방을 죽이고 비용도 커서 1차 방어로 쓰지 않고, 격리는 worker + 부모 감시로 한다. 시뮬은 `while(S.spawnT>=1)`(survivors.html 1540행)·`while(S.xp>=S.need)`(1322행) 같은 무한해질 수 있는 루프를 갖고, 병렬 세션이 계속 고친다.
- 부모 감시: 이벤트 루프 지연을 재서 2초 넘게 막히면 자가 종료(컨테이너 `restart: unless-stopped` 가 되살림). 틱 안에서는 NaN/Infinity 가드와 방별 틱 시간 상한을 둔다.
- Docker 한 장. Caddy 가 TLS. 메모리 상한 1GB. 로그는 `json-file` 크기·개수 제한(무제한 증가 방지).
- 한도(환경변수, §2.3.2 규칙): 동시 전투 방 3(측정 후 교정)·로비 6·총 연결 80, 인증된 소켓만 방 정원에 센다, **인증 전 연결은 IP당 3** 으로 따로 제한, IP당 WS 분당 20, uid당 1소켓.

### 7.2 입장·인증
1. 레이드 원점 로그인 페이지 → 봇 `POST /party/ticket {token, room?}`(토큰은 **본문**, `Authorization` 헤더 금지 — CORS 허용 헤더가 `Content-Type` 뿐) → `_nv_who`(디스코드+클랜원) → `{ticket, ws_url}`. 티켓 = HMAC-SHA256(uid, name, exp 60초, jti), **입장권 키 전용**. 응답 코드는 기존 `auth/rate/upstream/not_member` 체계 재사용.
2. 웹 → 레이드 서버 wss, 첫 메시지 `hello{proto, build, ticket}` (토큰·티켓을 URL·로그에 남기지 않음). 서버는 비밀키로 서명·만료·`jti` 재사용 검사.
3. 서버가 **세션 키**(7일, 회전)와 방 `resume_token` 을 발급한다. 이후 입장·재접속은 봇·디스코드 없이 `hello{session_key|resume_token}` 만으로.
4. **같은 uid 가 진행 중 방에 좌석을 갖고 있으면 티켓/세션 키 입장도 그 좌석을 되찾고**, 옛 소켓에는 4001 을 보낸다(인앱 브라우저·사파리·홈 화면 앱처럼 저장소가 다른 맥락 사이를 옮겨 다니는 경우).
5. **WebSocket 은 CORS 대상이 아니다**(검증이 짚음) → 레이드 서버가 핸드셰이크 `Origin`(레이드 원점)을 직접 검사. 비브라우저 시험은 환경변수로 허용.
6. 봇 부팅 직후 길드 캐시가 없으면 `_nv_who` 가 503 `[코드]` → 클라는 `Retry-After` 백오프. 봇의 디스코드 확인 한도(전역 분당 60, IP당 20)는 레이드 시작 4명에는 충분.

### 7.3 봇 ↔ 레이드 서버 계약 (호출 2개, 키 2개)
- 봇이 레이드 서버를 호출하지 않는다. 레이드 서버 → 봇 `POST /party/result {match_id, boss, outcome, t, build, seats[{uid, char, connected_ratio, alive, dmg, protected_s}]}` + HMAC(**결과 키 전용**). 입장권 키와 결과 키를 **분리**한다(한 키면 서버가 뚫릴 때 입장권과 보상 위조가 같이 된다). 봇은 `match_id` 로 멱등 처리, 200 이면 레이드 서버 outbox 삭제, 실패 시 지수 백오프 1시간 재시도. outbox 는 VPS 디스크 JSON(`write → rename`).
- 보상 금액은 **서버가 보스·난이도·클리어 여부로 계산**하고 클라이언트 숫자를 믿지 않는다. 멱등 키는 보상 받는 사람의 브장신 기록(`_brj_rec(uid)["party_done"]`, 최근 50개)에 두어 지급과 같은 `save_brj()` 로 저장한다(B등급). 경제 파일 단일 작성자는 계속 봇. 결과 접수 때 봇이 `_nv_member` 로 클랜원 여부를 다시 확인한다.
- 결과 접수는 **단계별**로(시작·페이즈·종료) 보낼 수도 있으나, 서버가 죽으면 판이 사라지는 것을 전제로 MVP 는 종료 시 1회로 한다(§7.6).

### 7.4 세션·재접속·자리비움 (서버 시간 기준, 수치는 JSON)
시계는 **서버가 마지막으로 받은 응용 메시지(입력·`hb`·`bg`)의 시각**부터 센다(§2.4 하트비트). 숨김 직전 최선 노력으로 `{t:'bg'}` 를 받으면 그 즉시 보호를 시작한다.

| 마지막 정상 수신 후 | 상태 | 효과 |
|---|---|---|
| 1.5초 경과 또는 `bg` 수신 | 선보호 | 받는 피해 -80%, 보스 표적 제외, **새 기믹 대상 선정에서 제외**, 무기 자동 공격 지속. 3초가 지나면 "자리 비움" 표시 |
| ~15초 | 자리비움 보호 | 위와 같음 |
| 15~45초 | 유령화 | 반투명, 피해 0·공격 0, 기믹 지정 대상 제외 |
| 45초~ | KO 취급 | 소생 가능, 20초 뒤 관전 |
- 이전 판의 "서버 ping 5초/응답 8초 후 0~15초 보호"는 iOS 가 앱 전환 즉시 JS 를 멈추면 **감지까지 최대 8초 동안 캐릭터가 조종자 없이 서 있고 보호도 없는** 구멍이 있었다(검토 C1). 그래서 1.5초 선보호 + `bg` 힌트로 바꿨다. 단위 시험에 "기믹 대상 지정 직후 감지 지연 8초" 케이스를 넣는다.
- 이미 기믹 대상으로 지정된 상태에서 이탈하면 서버가 안전 위치로 자동 이동(autopilot). 지정 전이면 대상 선정에서 제외.
- **한계(사장님께 그대로 알린다)**: 15초 안의 짧은 이탈만 보호다. 통화·긴 알림은 45초를 넘기기 쉽고 그동안 파티 화력이 줄며 광폭화 시계는 멈추지 않는다. 서버가 죽으면 판이 사라진다(§7.6).
- 악용 방지: 보호 상태 합계 판당 90초, 광폭화 시계 불정지, **보호/유령 합계가 5초를 넘은 판은 기록 보드·"무KO" 칭호에서 제외**. 파티장 "타임아웃" 1회/판(20초 전체 정지, 서버가 틱만 멈춤). R5 제안(동시 2명 이상 자리비움 시 최대 30초 자동 정지)은 선택 파라미터, 기본 끔 — 3단계 시험 후 결정.
- 복귀: 세션 키/`resume_token` 으로 즉시 합류, 전체 스냅샷, 3초 반투명 카운트다운, 요약 카드("지금 2페이즈, 보스 HP 38%, 다음 기믹: 감옥"). 레이드 모드에서는 로컬 일시정지를 쓰지 않는다(§3.1).
- 감지/대체: 프로토콜 ping 은 죽은 소켓용(5초 주기, 10초 무응답이면 닫음). 새 연결(같은 uid)이 옛 연결을 4001 로 대체. 클라 `p/q` 앱 레벨 핑으로 RTT.
- **로비**: 소켓이 끊기면 준비만 해제하고 **좌석은 180초 유지**(이전 60초 — 자동 잠금으로 쫓겨나는 문제, 검토 C1). 클라는 로비·카운트다운·관전에서도 Wake Lock(§3.1). 방 TTL: 연결된 사람 0명 5분, **로비는 마지막 활동(입장·준비·핑) 기준 슬라이딩 30분·최대 60분**, 전투 최대 25분(강제 종료, 보상 없음), 종료 60초 뒤 close. 청소 태스크 10초. 로비 동시 6방 상한이 방 12개 점거(uid당 시간당 3개)를 막는다.
- `pagehide`·백그라운드에서 `/party/leave` **호출 금지**(잠깐 나갔다 오는 것이 이번 문제의 본질). 명시 버튼만. 소켓으로 `bg` 힌트를 보내는 것은 허용.

### 7.5 배포·갱신 게이트
- **봇 자기 갱신**: `[코드]` `self_update`(bot.py 약 15437~15504행)는 10분마다 `squad-naejeon-bot` main 의 `bot.py` sha256 을 비교해 **다를 때만** 컴파일·메모리 제한 `--selfcheck` 를 거쳐 재시작한다(PZ/CQ/AKB/활성 초안이 있으면 최대 30분 미룸). 웹(`squad-analyzer`) 커밋은 봇을 재시작시키지 않는다. 이전 문서의 "10분마다 재시작"은 부정확하다. 봇 재시작은 입장권 발급을 수십 초 막고 결과 POST 를 지연시킬 뿐 진행 중 방은 영향 없음. 워치독·SIGTERM·OOM 재시작은 어차피 못 막으므로 재접속·outbox 가 2차 방어선. 봇 안에 방을 두는 대안을 고를 경우에만 `self_update()` 의 해시 비교 직후·`bot_new.py` 쓰기 직전에 게이트를 넣는다(R4 §3.3).
- **레이드 서버 배포**: CI(Actions)에서 이미지 빌드(번들 포함) → 서버. **드레인 방식**: 신규 방 금지 → 진행 방 종료 대기(최대 25분) → 교체. 방 0개일 때만 자동 교체, 강행은 사람 승인. **직전 이미지 태그 2개 보관, health-gated 배포(새 이미지의 `/health` 가 통과해야 전환), 실패 시 자동 되돌림.** 번들이 이미지 안에 있으므로 서버와 클라가 같이 롤백된다. 봇의 `bot_prev.py`/`.update_pending` 롤백과 워치독은 봇호스팅 패널용이라 Vultr 로 옮겨지지 않는다. 이 단계에서는 Actions 실행·배포 금지.
- **개발 기간 주의**: 봇은 `bot.py` 커밋 기준 하루 7~18회 갱신 후보가 생긴다(`git log` 로 날짜별 센 값: 9/28 17~18, 9/29 7~8, 10/1 11, 10/7 12~15 — 날짜 경계 KST/UTC 에 따라 ±3, 이전 판의 12·6 은 틀렸다. 같은 10분 안의 커밋은 한 번의 재시작으로 합쳐질 수 있다). 로비 시험은 갱신을 끈 시험 인스턴스에서만.
- **웹**: 레이드 원점은 번들이 해시 경로라 `BUILD_ID` 문제가 없다(진입 `/` 만 no-cache). 솔로 `index.html` 은 기존 `BUILD_ID` 규칙 유지.

### 7.6 장애·일관성
- 단일 장애점: VPS 1대. 방이 소수라 허용, 워치독(`/health` 5분 연속 실패 시 재기동)과 디스코드 웹훅 알림.
- 진행 중 판은 서버 프로세스가 죽으면 사라진다. 시뮬 상태는 `S.dq` 클로저와 객체 참조 때문에 JSON 직렬화가 안 된다 `[코드]` → **판 복구는 MVP 범위 밖**(방 사라짐 안내, 보상 없음). 사장님의 원래 불만 "게임이 날아간다"는 레이드에서 **서버 장애·교체 시** 다른 형태로 남는다 — E8(`dq` 데이터화)이 끝나면 N초 스냅샷 복구를 재검토.
- **입구 킬스위치**: 클라는 레이드 서버 `/health`(또는 봇 응답)의 `open` 값을 보고 입구 버튼을 "점검 중"으로 바꾼다. 원격으로 끌 수 있다. 서버 장애·배포 중 버튼이 눌려 4명이 로비에서 원인 모른 채 멈추는 일을 막는다.
- 방 상태 파일 저장(R4 `party_rooms.json`)은 로비 복구용으로만 선택. MVP 는 로비도 메모리.

### 7.7 관측
`/health`: `{up, build, proto, open, rooms:{lobby,playing}, conns, peak, tick_ms:{p50,p99,max}, loop_delay_ms:{p99}, rss_mb, closes:{코드:n}, rej:{사유:n}, resume:{ok,fail}, outbox, draining}`. `closes[1012/1006]` 구분으로 "재시작 때문인지 네트워크 때문인지" 분리. 로그 접두 `[raid]`, uid 앞 4자리만. 봇 쪽 `signals.py` 가 이 `/health` 를 읽는 신호 추가는 A등급(관측) — 샌드박스에서 직접 못 닿으면 기존 릴레이 방식으로.

### 7.8 남용 방지
클랜원만(`_nv_who`), 1인 1방, 방 생성 5초 쿨다운·시간당 3개, 로비 동시 6방, 입장권 만료·재사용 거절, 실패 join uid당 분당 10, 프레임·속도 제한, Origin 검사, 입력 벡터 크기 제한, 인증 전 연결 IP당 3, 보상 일일 상한·이상치 로그(`_p6_anomalies` 방식), 보호 시간 기록 제외. 서명 키·토큰은 환경변수/시크릿에만(코드·커밋 금지), 키는 입장권/결과 두 개.

### 7.9 시험 전략
단위: 방 상태기계 순수 함수(디스코드·네트워크·시계 주입), 멱등 지급, 자리비움 상태기계(감지 지연 케이스 포함). 통합: 가짜 클라 4개. 장애: §4 2단계 목록. 부하: 방 3개 × 4 가짜 클라(합격)와 8방(스트레스·거절 확인)을 **서울 VPS 에** 붙여 CPU·틱 p99·루프 지연·대역폭 실측(샌드박스 부하가 높으므로 `uptime` 을 같이 기록하고 상대 비교). 브라우저: Playwright Chromium 4페이지 + **CDP 수명주기**(`Page.setWebLifecycleState`, 네트워크 오프라인) + 같은 uid 두 컨텍스트 + Slow 4G 복귀 시간. 실기기: 안드로이드 표(사장님)·아이폰 표(지원자)와 소켓 생존 시험 페이지. 내부창 폐기 흉내는 Chromium 으로. 서버 CI: `survivors.html` 변경마다 Node 로드·4액터 900초·ESLint(§4).

### 7.10 운영 런북 (신규, 검토 C2 — 최소 한 장)
- **프로비저닝**: 서버 생성 시 붙여 넣는 스타트업 스크립트(cloud-init) 한 장이 Docker·Caddy·방화벽을 설정하고, 이후 갱신은 서버가 이미지를 가져오는 방식 또는 Actions SSH 중 0단계가 정한다 `[실측]` 샌드박스 22번 포트는 막혀 있으므로 에이전트가 직접 SSH 로 만지지 못한다.
- **소스 위치**: 레이드 서버·번들 조립 스크립트는 `squad-analyzer` 저장소의 `raid/` 디렉터리, 번들 고정은 `raid/PIN`. CI 트리거는 `raid/**` 또는 `PIN` 변경.
- **주소 설정**: 레이드 원점은 도메인 하나(DNS 만 바꾸면 서버를 옮길 수 있음). 봇이 읽는 `ws_url` 은 설정값(봇 환경변수 변경 = 봇 재시작이 필요하므로 도메인으로 흡수).
- **재부팅**: 자동 보안 업데이트의 자동 재부팅은 끄고, 방 0개인 예약 창에서만 재부팅한다. 로그 로테이션.
- **키 범위**: `[외부]` Vultr API 키는 서비스별 범위를 못 정하고(계정 전체) 접근 제어(IP 허용 목록)가 유일한 제한이며 Vultr 는 "모든 IPv4 허용"을 권장하지 않는다. 그래서 **API 키가 필요 없는 경로를 기본**으로 한다(사장님이 서버 1대를 화면에서 직접 만들고 스타트업 스크립트를 붙여 넣기 — README).
- **백업**: 서버에 남는 상태는 outbox 정도라 백업은 선택. Vultr 자동 백업은 플랜의 +20%(5달러면 약 $1), 스냅샷은 $0.05/GB-월 `[외부]`. 서버 재구축은 스타트업 스크립트 + DNS 변경으로 한다.
- **모니터**: `/health` 5분 연속 실패 → 디스코드 웹훅. 루프 지연 p99·틱 p99·`closes` 를 `signals.py` 로.
