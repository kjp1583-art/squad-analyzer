### 1.1 사장님 문제의 정확한 원인 (재현함)
- `[실측]` 폰 크기 Chromium 에서 20초 플레이 → 화면 숨김 → `pause` 로 멈춤(정상) → 다시 보여도 `pause` 유지 → **새로고침(= 브라우저가 메모리 회수로 버렸다 다시 여는 상황)하면 상태 `title`, S 객체 없음.** (R5 life.py, 검증이 재실행해 재현)
- `[코드]` `survivors.html` 은 visibilitychange(hidden)·blur 에서 `pauseGame()` 만 부르고 판 상태를 어디에도 저장하지 않는다. 판 저장·`pagehide`·`wasDiscarded` 코드 0건.
- "웹 팝업창"의 정체는 `[미확인]`. 코드는 같은 탭 이동 링크뿐(`target` 없음, `window.open` 0건). 디스코드 앱 안의 인앱 브라우저일 가능성이 있으나 확인 못 함 → 사장님께 질문(§10 D13).
- 결론: 웹이라서가 아니라 **솔로가 판을 폰 메모리에만 들고 있어서** 생긴다. 레이드는 서버가 판을 들고 있어 구조적으로 사라지고, 솔로는 별도 작업 "이어하기"(#12, 다른 에이전트 진행 중)가 맡는다. 중복 구현 금지.

#### 2.3.1 스파이크가 증명한 것 / 못 한 것 (R2, 검증이 재실행)
- `[실측]` `survivors.html` 의 두 번째 `<script>` 를 document/canvas/Audio 스텁(약 15줄)만으로 Node `vm` 에 수정 없이 로드, `update(dt)` 렌더 없이 구동.
- `[실측]` 4액터 컨텍스트 교체 패치(약 60줄 + update 재배열)로 4인 5조합 × 900초(27,000틱, 보스 포함) 예외 0, 무기 39종 전수 90초 예외 0(39/39 피해 기록). 같은 시드·같은 입력이면 120초간 매초 상태 해시 일치.
- `[실측]` 방 = vm 컨텍스트: 8개 로드 228ms, 힙 +6.8MB.
- `[실측]` 패치 도중 612초 시점에 평범한 플레이로는 안 밟는 `ReferenceError`(`p`)가 처음 터짐 → 장시간·전 조합 시험과 ESLint `no-undef` 가 필수(CLAUDE.md "장비를 끼워라"와 같은 교훈).
- **못 한 것**: 풀 소유자 필터(13개 풀) 미구현이라 부메랑·로켓·펫·훅 등은 액터 수만큼 중복 갱신 — 예외만 없고 **의미는 틀림**. 레벨업은 첫 카드 자동 선택. 연출 이벤트 추출·네트워크·클라 그리기는 0%. 클라 뷰가 전체 작업의 절반 이상(L)이다.

#### 2.3.2 서버 비용 규모 (정정 반영)
- R2 원 수치 "4인 30Hz = 코어 5%" 는 **초반 240초 값**이다(검증 corrected). 15분 전체 평균은 부하 3 상태에서 CPU 3.2ms/틱(벽시계 2.4ms) = 코어 약 **7~10%**, 후반(적 220마리 상한)은 더 높다 `[실측]`.
- R1 의 "방 1개 7~23%, 3~8방/vCPU" 는 단일 플레이어 측정에 ×8(인원·적)·×2(느린 vCPU) 가정을 곱한 **추정**이다(검증 corrected). 측정은 LOW 모드(적 상한 140)였다.
- 이 문서의 계획치: **방 1개 = 코어 15~20% 가정 → vCPU 1개당 3방(12명)**으로 설계한다. 레이드는 잡몹 동시 40~60(R3 제안)이라 실제는 더 가벼울 가능성이 크지만 `[미확인]`. 단계 0·1 에서 서울 VPS 실측으로 교정한다.
- 틱 스파이크: 단일 플레이어 p99 가 1.4~11ms(부하 의존)라 4인에서는 한 틱(33ms) 근접 가능 `[추정]`. 고정 시간 단계 루프 + 틱 시간 계측 + 지연 시 15/20Hz 폴백을 설계에 넣는다.

### 2.4 프로토콜

- **전송**: WebSocket(wss), 바이너리 스냅샷 + JSON 제어 메시지. 순서 보장 TCP 이므로 직전 대비 델타를 ACK 없이 쓸 수 있다. 헤드오브라인 블로킹 위험은 §9. WebTransport/WebRTC 데이터채널은 Safari 지원 `[미확인]` 이라 쓰지 않는다.
- **틱**: 서버 시뮬 30Hz 고정 dt=1/30(원본 dt 상한 0.05 안, 하네스가 검증한 영역). 스냅샷 15Hz(2틱마다). 입력 15~30Hz. 서버 루프는 hrtime 누적기, 따라잡기 최대 3틱. 폴백 20/10Hz.
- **입력(C→S)**: `{seq u16, 방향 각도+세기 2B, 버튼 1B}`. 서버가 벡터 크기를 1로 제한(속도 위조 방지).
- **스냅샷(S→C)**: 적은 활성 슬롯 비트맵 + 마리당 dx,dy int8 + hp/플래그 = 마리당 약 3B(델타) / 7B(전체). 플레이어 4명 각 8B(+본인 정밀 10B), 보스 약 20B. `[추정]` 클라당 다운 10~35KB/s(적 300마리 가정 — 실제 상한은 220/140), 15분 레이드 15~32MB. 실제 전송 측정은 없다(검증: 산식이며 measured 가 아님).
- **이벤트**: 투사체 생성(종류·시작점·각도·속도·수명), 폭발, 피격 숫자, 소리, 배너는 상태가 아니라 이벤트로 별도 전송(1~3KB/s `[추정]`). 투사체는 직선이라 클라가 진행시킨다. 서버 스텁이 `AU/EX/txt/banner/taunt/say` 호출(약 145곳)을 이벤트 큐로 바꾼다 — Proxy 한 겹.
- **본인 이동**: 클라가 즉시 적용(예측), 서버의 유효 속도·강제 이동(끌림·기절·감옥)을 받아 보정(8px 미만 부드럽게, 크면 스냅). 타인·적: 약 100~130ms 뒤 시점으로 두 스냅샷 사이 보간.
- **하트비트**: 서버 ping 5초, 응답 8초 없으면 자리비움 표시(소켓 `onclose` 에 의존하지 않음 — iOS 에서 안 오는 사례). 클라: 보이는 상태에서 3~4초 무수신이면 스스로 소켓을 닫고 재접속.
- **버전**: `hello{v, build}` — 시뮬 빌드 해시가 서버와 다르면 `err update` 후 close 4002, 클라가 `BUILD_ID` 캐시를 갱신해 새로고침. 클라와 서버는 **같은 `survivors.html` 커밋**에서 나온 시뮬을 써야 한다.
- **close 코드**: 1000 정상 · 1008 남용 · 1009 큼 · 1012 서버 재시작(즉시 재접속) · 4001 다른 기기로 대체 · 4002 버전 · 4003 추방 · 4004 방 없음.
- **한도**: 클라→서버 프레임 ≤4KB, 서버→클라 ≤16KB(풀 스냅샷 재전송 제외), 연결당 40msg/s(버스트 80), 핸드셰이크 후 5초 안에 hello.

### 3.1 체크리스트
`[코드]` 현황: manifest·서비스워커·`apple-mobile-web-app-*` 메타는 어느 html 에도 없다(`manifest.json` 2개는 이미지 목록). 아이콘은 `index.html` 만 favicon+apple-touch-icon(data URI)이 있고 `survivors.html` 은 `<link rel="icon" href="data:,">`(빈 아이콘), `logo.png` 는 128×128. `survivors.html` 은 `viewport-fit=cover` 이나 `env(safe-area-inset-*)` 처리 0건(HUD 고정 8px), 캔버스 CSS 는 `100vw/100vh`. 조이스틱은 단일 `joy.id` 를 `pointerdown` 에서 무조건 덮어써 **두 번째 손가락이 스틱을 가로챈다**(코드 읽기; 멀티터치 실행 시험은 안 함).

### 3.2 로그인
- `[코드]` 현재 디스코드 implicit OAuth(`response_type=token`), 토큰은 해시로 돌아와 `localStorage.sgg_dc`(7일). 만료 24시간 전에는 같은 창을 `discord.com` 으로 보내는 `prompt=none` 자동 갱신. 복귀는 메인 페이지(index)로 와서 `sessionStorage` 의 `sgg_oauth_return` 으로 게임에 되돌린다.
- `[외부]` 아이폰 홈 화면 앱은 사파리와 저장소가 분리되고(WebKit 181849 "by design"), 범위 밖 링크는 인앱 브라우저로 열려 저장소를 공유하지 않는다(Firtman, 2023-06 — iOS 26 반영 `[미확인]`). OAuth 복귀가 PWA 로 안 돌아오는 포럼 보고가 다수(Apple 포럼 810832 등). **디스코드 흐름이 실제로 어떻게 되는지는 아무도 확인 못 했다.**
- iOS 26 은 홈 화면에 추가한 모든 사이트를 기본 웹앱으로 연다(WebKit 16993, 끄는 스위치 있음) → 이미 `survivors.html` 을 추가한 클랜원은 지금 standalone 으로 열리며 로그인이 깨졌을 수 있다 `[미확인]`.
- **설계**: 확인표 5번(사장님) 결과로 분기한다.
  - 정상 복귀 → 기존 로그인 유지, 입장권만 봇에서 받는다.
  - 깨짐 → **중계 로그인**: 앱이 랜덤 `state` + 짧은 확인 코드를 만들고 → 디스코드 승인 창 → 도착 페이지가 토큰+state 를 봇에 올리고 → 봇이 uid 를 검증해 장기 세션 열쇠(서버가 폐기 가능)를 발급 → 앱이 state 로 폴링해 받는다. 로그인 고정 공격 방지로 두 화면에 같은 확인 코드를 보여 준다. 대안: 봇 슬래시 명령으로 6자리 코드 입력. 새 리다이렉트 URI 가 필요하면 **디스코드 개발자 페이지 등록은 사장님**이 한다(§10).
- 레이드 세션 중에는 디스코드 토큰을 쓰지 않는다: 입장권 → 레이드 서버의 `resume_token` 으로 재접속(§7).

### 3.3 아이폰에서 자동 시험이 못 보는 위험
샌드박스에는 Playwright Chromium 만 있다. 아래는 전부 `IPHONE_CHECKLIST.md` 로 넘긴다.
1. 홈 화면 앱 로그인 복귀 위치와 로그인 유지(최대 위험).
2. 앱 전환·화면 잠금 뒤 WS `readyState`·`onclose` 동작과 재접속 시간.
3. 오디오 인터럽트 복구, 무음 스위치, 소리 재생 여부.
4. 노치/다이내믹 아일랜드 안전영역, `100vh` 가 아래를 가리는지(아이폰 주소창 접힘 높이 함정은 일반 지식이며 출처 확인 못 함).
5. 가장자리 스와이프 뒤로가기·시스템 제스처 충돌, 두 손가락 조작, 핀치/더블탭 확대.
6. 메모리 부족으로 페이지가 버려지는 빈도, 저전력 모드 성능, 오래된 아이폰 캔버스 메모리(캔버스 1개 16.8Mpx, 전체 224~384MB 보고 `[외부]` — 우리 메인 캔버스 약 1.4Mpx·5.7MB, 협곡 바닥 캐시 상한 약 64MB(코드 상한, 서버 레이드에서는 쓰지 않을 수도 있음)).
7. 디스코드 인앱 브라우저의 동작(UA 로 감지하는 방법 `[미확인]`).
8. WebSocket 이 백그라운드에서 몇 초 뒤 닫히는지(현재 iOS 정확치 `[미확인]`; 포럼 보고뿐).
9. 웹 푸시, 진동, 방향 잠금(안 되는 것이 정상이지만 확인).

### 3.4 성능 예산
- `[실측]` 모바일 에뮬(412×860@2x, 캔버스 1.42Mpx) update 중앙값 0.2~0.9ms vs draw 5~20ms(적 30→140마리, CPU 스로틀 4~6x 에서 21~26ms) — **프레임의 95% 이상이 그리기**(검증이 load 13.7 에서 재현). 실행 간 편차가 2배라 합격 판정에 쓰지 않는다. 폰 프로필이 데스크톱 대비 draw 2~2.5배.
- 레이드는 클라 엔티티가 솔로 호드(140+)보다 적다(보스+잡몹 40~60+플레이어 4+이펙트) → **Canvas2D 로 시작.** 승격 조건(제안): 중급 안드로이드·구형 아이폰 실기기에서 레이드 실전 장면이 30fps 아래로 5초 이상이면 해당 층만 WebGL. 먼저 쓸 값싼 수단: DPR 상한 1.5, 프레임 시간 감시 자동 하향, 네트워크 틱과 렌더 분리.
- 예산(제안): 클라 다운 ≤40KB/s 피크, 렌더 프레임 ≤24ms 평균(60프레임), 메인 캔버스 ≤3Mpx.

## 6. 레이드 MVP 명세 — 「또뀨의 진실의 방: 재판 레이드」

**R3 기획 기반, 독립 검증 없음. 아래 수치는 모두 초안이며 3단계 시험으로 조정한다.** 새 대사는 사장님 승인 전까지 "초안", 기존 코드 대사만 쓰면 승인 불필요.

### 6.1 왜 또뀨인가
`[코드]` `BOSS.ddo`(반경 46, 속도 56, hp 1300(기본, `bossMul` 로 스케일), atk `room`,`shots`)와 진실의 방(감옥)·`sp0/hit/dead/win` 대사가 이미 있다. 디스코드 월드보스로 친숙하고, 분산·감옥 구출·순서 맞추기가 개그("해명", "회의록", "딱 3시간")와 맞는다. 한 판 약 12~13분, 2페이즈, 15분 초과 시 "회의 시간 초과" 패배.
이름은 기존 디스코드 월드보스("공격" 채팅, 전설 드롭, `RAID_BOSSES`)와 겹치지 않게 **"파티 레이드"/"재판 레이드"** 로 한다.

### 6.2 조작과 역할
- 고유 무기는 지금처럼 **자동 발사**. 손가락은 이동 + **역할 버튼 1개**(자동 사용 기본 ON, 수동으로 맞추면 효과 +15%). 한 손 플레이 가능.
- 능력치 표준화(솔로 해금·진행도·장비는 전투력에 영향 없음): 표준 HP 300(탱커 390), 속도 180. 방어 고정값은 비율로 환산(arm1/2/3 = 받는 피해 -3/-6/-9%). 피해 단위는 "표준 HP 300 대비 %".
- 무기 성장은 카드 없이 시간 기준: 고유 무기 Lv3 시작, 2분마다 +1, 10분 Lv8, 2페이즈 시작에 각성 자동. 페이즈 시작에 공용 무기 1/유물 1 8초 선택(비정지).
- 역할 버튼(쿨타임 초안): 탱커 [도발 외침] 18초(4초 우선 표적+받는 피해 -50%) / 서포터 [응원] 18초(반경 200 아군 HP +30%, 2초 보호막, 소생 ×1.5) / 제어 [속박] 16초(반경 잡몹 2초 기절, 보스 경직 게이지 +15%) / 딜러 [몰아치기] 25초(5초간 피해 +35%, 경직 중 ×1.5).
- 17명 배정(R3, 코드 기준): 탱커 3(ddmj·yj·tw) / 서포터 3(ssu·amd·kyo) / 제어 5(sr·ddo·eom·hrb·bgb) / 딜러 6(jjg·ildj·brj·psg·mms·yumi). 같은 캐릭터 중복 불가(주간 특별 룰만 허용). 상점 캐릭터(yumi·eom)는 후원 가치 보호를 위해 **주간 대여 대상에서 제외**.

### 6.3 맵과 보스
- 원형 아레나 반지름 760(지름 1520), 중앙 단상에 보스, 가장자리 4곳(중심에서 520)에 "증언대" ①~④(색+모양+숫자로 색약 대응), 외곽 6방향 졸개 등장구, 아레나 밖은 벽. `[코드]` 폰 세로(390×844)의 보이는 월드는 약 557×1206(SC 하한 0.7) — 지름 1520 은 한 화면에 안 들어가므로 **미니맵·가장자리 화살표 필수**, 레이드 전용 시야 배율 완화 검토.
- 보스 체력 = **D × 1980**(D = 1인 표준 DPS, 4인 공식 D×4×0.75×660초). **D 는 아직 측정 안 했다** — `tests/survivors_unique_weapons_test.py` 의 `dmgBy` 방식으로 허수아비 보스에게 12~20초 쏘아 무기별 D 를 구하고 역할 보정(탱 ×0.6·서 ×0.5·제 ×0.7·딜 ×1.2, 초안)을 곱한다. 1페이즈 100→55%, 2페이즈 55→0%.
- 인원 스케일(4인=1.00): 보스 HP 1인 0.30 / 2인 0.55 / 3인 0.78 / 4인 1.00. 졸개 웨이브 4/6/7/8. 연결 사슬: 1인 없음, 2인 서로, 3~4인 무작위 2명. 감옥 열쇠 기둥: 1인 자동, 2~3인 1개, 4인 2개. 광폭화 16/16/15/15분. 협동 기믹은 **한 번에 하나**, 앞 기믹 종료 후 최소 4초 간격.

## 7. 서버·세션·운영 설계

### 7.1 프로세스
- 레이드 서버: Node 22 + `ws`, 단일 프로세스, 방당 vm 컨텍스트(스파이크로 8개 228ms·+6.8MB), 방 인터페이스를 추상화해 필요 시 `worker_threads`/프로세스 분리. 방 하나가 예외로 죽어도 다른 방에 영향이 없게 **틱마다 try/catch**, 예외 시 그 방만 종료(보상 없음, 알림).
- Docker 한 장. Caddy 가 TLS(Vultr 선택 시). `restart: unless-stopped`. 메모리 상한 1GB(Vultr) / 512MB~1GB(Fly). 방 10개 약 160~270MB `[추정]`(방당 10~20MB 가정).
- 한도(환경변수): 전역 방 12·연결 80(실측 후 조정), IP당 WS 분당 20, uid당 1소켓.

### 7.2 입장·인증
1. 웹 → 봇 `POST /party/ticket {token, room?}`(토큰은 **본문**, `Authorization` 헤더 금지 — CORS 허용 헤더가 `Content-Type` 뿐) → `_nv_who`(디스코드+클랜원) → `{ticket, ws_url}`. 티켓 = HMAC-SHA256(uid, name, exp 60초, jti). 응답 코드는 기존 `auth/rate/upstream/not_member` 체계 재사용.
2. 웹 → 레이드 서버 wss, 첫 메시지 `hello{v, build, ticket}` (토큰·티켓을 URL·로그에 남기지 않음). 서버는 비밀키로 서명·만료·`jti` 재사용 검사.
3. 서버가 `resume_token` 발급. 이후 재접속은 봇·디스코드 없이 `hello{resume_token}` 만으로.
4. **WebSocket 은 CORS 대상이 아니다**(검증이 짚음) → 레이드 서버가 핸드셰이크 `Origin`(`https://kjp1583-art.github.io`)을 직접 검사. 비브라우저 시험은 환경변수로 허용.
5. 봇 부팅 직후 길드 캐시가 없으면 `_nv_who` 가 503 `[코드]` → 클라는 `Retry-After` 백오프. 봇의 디스코드 확인 한도(전역 분당 60, IP당 20)는 레이드 시작 4명에는 충분.

### 7.3 봇 ↔ 레이드 서버 계약 (호출 2개)
- 봇이 레이드 서버를 호출하지 않는다. 레이드 서버 → 봇 `POST /party/result {match_id, boss, outcome, t, build, seats[{uid, char, connected_ratio, alive, dmg}]}` + HMAC. 봇은 `match_id` 로 멱등 처리, 200 이면 레이드 서버 outbox 삭제, 실패 시 지수 백오프 1시간 재시도. outbox 는 VPS 디스크 JSON(`write → rename`).
- 보상 금액은 **서버가 보스·난이도·클리어 여부로 계산**하고 클라이언트 숫자를 믿지 않는다. 멱등 키는 보상 받는 사람의 브장신 기록(`_brj_rec(uid)["party_done"]`, 최근 50개)에 두어 지급과 같은 `save_brj()` 로 저장한다. 경제 파일 단일 작성자는 계속 봇.
- 결과 접수는 **단계별**로(시작·페이즈·종료) 보낼 수도 있으나, 서버가 죽으면 판이 사라지는 것을 전제로 MVP 는 종료 시 1회로 한다(§7.6).

### 7.4 세션·재접속·자리비움 (서버 시간 기준, 수치는 JSON)
| 구간 | 상태 | 효과 |
|---|---|---|
| 0~15초 | 자리비움 보호 | 보스 표적 제외, 받는 피해 -80%, 무기 자동 공격 지속, "자리 비움" 표시 |
| 15~45초 | 유령화 | 반투명, 피해 0·공격 0, 기믹 지정 대상 제외 |
| 45초~ | KO 취급 | 소생 가능, 20초 뒤 관전 |
- 이미 기믹 대상으로 지정된 상태에서 이탈하면 서버가 안전 위치로 자동 이동(autopilot). 지정 전이면 대상 선정에서 제외.
- 악용 방지: 보호 상태 합계 판당 90초, 광폭화 시계 불정지. 파티장 "타임아웃" 1회/판(20초 전체 정지, 서버가 틱만 멈춤). R5 제안(동시 2명 이상 자리비움 시 최대 30초 자동 정지)은 선택 파라미터, 기본 끔 — 3단계 시험 후 결정.
- 복귀: `resume_token` 으로 즉시 합류, 전체 스냅샷, 3초 반투명 카운트다운, 요약 카드("지금 2페이즈, 보스 HP 38%, 다음 기믹: 감옥").
- 감지: 서버 ping 5초/8초 무응답 → 자리비움. 클라 `p/q` 앱 레벨 핑으로 RTT. 새 연결이 옛 연결을 4001 로 대체(반쯤 죽은 소켓이 좌석을 붙잡지 않게).
- 로비: 이탈 시 준비 해제, 좌석 60초 유지. 방 TTL: 연결된 사람 0명 5분, 로비 최대 60분, 전투 최대 25분(강제 종료, 보상 없음), 종료 60초 뒤 close. 청소 태스크 10초.
- `pagehide`·백그라운드에서 `/party/leave` 호출 금지(잠깐 나갔다 오는 것이 이번 문제의 본질). 명시 버튼만.

### 7.5 배포·갱신 게이트
- **봇 자기 갱신(10분)**: `squad-naejeon-bot` main 의 `bot.py` sha256 이 다를 때만 `os.execv` 재시작 `[코드]`. 웹(`squad-analyzer`) 커밋은 봇을 재시작시키지 않는다. 봇 재시작은 입장권 발급을 수십 초 막고 결과 POST 를 지연시킬 뿐 진행 중 방은 영향 없음. 워치독·SIGTERM·OOM 재시작은 어차피 못 막으므로 재접속·outbox 가 2차 방어선. 봇 안에 방을 두는 대안을 고를 경우에만 `self_update()` 의 해시 비교 직후·`bot_new.py` 쓰기 직전(자식 selfcheck 기동 전)에 게이트를 넣는다(R4 §3.3, 검증 확인).
- **레이드 서버 배포**: CI(Actions)에서 이미지 빌드 → 서버. **드레인 방식**: 신규 방 금지 → 진행 방 종료 대기(최대 25분) → 교체. 방 0개일 때만 자동 교체, 강행은 사람 승인. `/health.build`(시뮬 빌드 해시)로 클라와 불일치 감지. 이 단계에서는 Actions 실행·배포 금지.
- **개발 기간 주의**: 봇은 하루 6~18회 재시작(9/28 18건·9/29 8건·10/1 12건·10/7 6건, 검증 확인). 로비 시험은 갱신을 끈 시험 인스턴스에서만.
- **웹**: `index.html` `BUILD_ID` 를 올려야 캐시를 넘는다. 서비스워커를 도입하면 버전 키·강제 갱신 경로 필수.

### 7.6 장애·일관성
- 단일 장애점: VPS 1대. 방이 소수라 허용, 워치독(`/health` 5분 연속 실패 시 재기동, 기존 패턴 복제)과 디스코드 웹훅 알림.
- 진행 중 판은 서버 프로세스가 죽으면 사라진다. 시뮬 상태는 `S.dq` 클로저와 객체 참조 때문에 JSON 직렬화가 안 된다 `[코드]` → **판 복구는 MVP 범위 밖**(방 사라짐 안내, 보상 없음). E8(`dq` 데이터화)이 끝나면 N초 스냅샷 복구를 재검토.
- 방 상태 파일 저장(R4 `party_rooms.json`)은 로비 복구용으로만 선택. MVP 는 로비도 메모리.

### 7.7 관측
`/health`: `{up, build, rooms:{lobby,playing}, conns, peak, tick_ms:{p50,p99,max}, rss_mb, closes:{코드:n}, rej:{사유:n}, resume:{ok,fail}, outbox, draining}`. `closes[1012/1006]` 구분으로 "재시작 때문인지 네트워크 때문인지" 분리. 로그 접두 `[raid]`, uid 앞 4자리만. 봇 쪽 `signals.py` 가 이 `/health` 를 읽는 신호 추가는 A등급(관측).

### 7.8 남용 방지
클랜원만(`_nv_who`), 1인 1방, 방 생성 5초 쿨다운·시간당 3개, 입장권 만료·재사용 거절, 실패 join uid당 분당 10, 프레임·속도 제한, Origin 검사, 입력 벡터 크기 제한, 보상 일일 상한·이상치 로그(`_p6_anomalies` 방식). 서명 키·토큰은 환경변수/시크릿에만(코드·커밋 금지).

### 7.9 시험 전략
단위: 방 상태기계 순수 함수(디스코드·네트워크·시계 주입), 멱등 지급, 자리비움 상태기계. 통합: 가짜 클라 4개. 장애: §4 2단계 목록. 부하: 방 8~25개 × 4 가짜 클라를 **서울 VPS 에** 붙여 CPU·틱 p99·대역폭 실측(샌드박스 부하가 높으므로 `uptime` 을 같이 기록하고 상대 비교). 브라우저: Playwright Chromium 4페이지. 아이폰: 확인표.
